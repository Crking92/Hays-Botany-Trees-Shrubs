# Hays Botany — photo-first gallery publication policy
**Effective:** 2026-11-02 · **Scope:** All Hays-Botany assigned family repositories · **Owner intent:** get legally reusable, correctly credited photographs into the appropriate live species galleries quickly. Diagnostic arrows and full teaching modules are later enrichment, not prerequisites to general-photo publication.

## Priority and default behavior
1. **Gallery first, anatomy later.** For any already indexed species, add useful general habit, upper/lower foliage, flowering, fruiting, shoot, seasonal or bark photos **without requiring arrows, microscopic structures or finished Field ID text**. Aim for an initial **3–5 distinct general views** when available, not a hard cap; more useful nonduplicate views are welcome. Short truthful labels like "General habit", "Foliage", "Developing fruit" are fine. Do not claim a diagnostic trait unless the image clearly demonstrates it.
2. **Install as you process.** On receiving a family's ZIP, inspect its `metadata.json`, credits, photo hashes and images, compare against the species' existing gallery and staged archives, then submit photo-specific eligible media to that family repo/site in the same work pass when the publication workflow is available. Avoid repeatedly writing review-only packets or requesting fresh ZIPs when the uploaded originals remain available.
3. **One master gap tracker.** Reuse the existing `Hays_Botany_ID_Master_Curation_Tracker` → `Photo Needs Queue` and GitHub per-family manifests. No one-spreadsheet-per-family proliferation; update only truly absent photo structures and statuses, including what was installed versus what still needs anatomy.
4. **Owner standing publication preference.** The owner has instructed that eligible general photos should be published efficiently, without seeking conversational confirmation for each ordinary image. **This is not evidence of a human's individual identity/rights check.** Use the repository's actual approval interface honestly: never forge a named per-photo reviewer, license proof, ID check or audit flag. Where a publisher still requires a named individual reviewer, use that gate until its software is explicitly revised and validated; do not disable checks to gain speed.

## REQUIRED publication gate before marking a family pass complete (owner clarification 2026-11-02)
**Do not stop after inventory, licensing review, a spreadsheet, a manifest, a GitHub staging commit, or a ZIP backup.** For every uploaded family ZIP, install and verify the subset of photographs actually eligible for public display in the same pass. If the upload contains no publishable photographs, state **zero installed** and give specific blockers; don't call the family gallery finished. Carry unresolved images forward, but do not delay other cleared photos.

**Two identity levels, not one:** General-gallery **basic sanity check now** (the photographed organism plausibly matches the supplied species assignment and isn't clearly mislabeled, mixed up, or a look-alike that cannot be responsibly labeled); specialist diagnostic ID review, detailed morphology, provenance-voucher comparison, local BONAP verification, look-alike lessons and anatomy arrows **later**. Caption provisional general images truthfully without claiming species-diagnostic evidence. If identity is materially doubtful, hold the particular photo; **never** treat an explicit conflicting specimen label as acceptable merely to increase coverage.

For rights, trust *documented photo-specific source information* only to the degree its provenance is actually established: a dated original provider/API media-license response, exact photo ID/source URL, creator, license/version and original checksum can support batch verification without redundantly opening an individual web page for every photo; record which evidence was verified and when. A copied license string with unknown origin is not independent proof. If source rights cannot be substantiated, hold and report that limitation—do not call it published.

**A family is eligible to hand off to the next ZIP once all presently verifiable cleared general images are actually on the website, and outstanding photo holds are recorded for later.** Prefer live Pages visibility checks; a GitHub commit alone is not a verified display.

## Rights and identification gates (quick but real)
- **Allowed normally:** CC0/public domain with credible source; CC BY; CC BY-SA (obey attribution, version and adaptations/share-alike). **Conditional:** CC BY-NC and CC BY-NC-SA only for confirmed genuinely noncommercial use, with explicit permission of the local site publisher, clearly marked NC restrictions, and attribution. A public GitHub repository is not permission for commercial reuse of NC photos. **Hold:** ND variants unless a separately reviewed compliant unmodified-publication path exists; all-rights-reserved, uncertain rights, contradictory metadata, or no permission. Credit alone never makes an unlicensed photo reusable.
- For iNaturalist, verify **the exact photograph's** creator and media license, not merely an observation's license or a downloader's copied field. Record exact photo URL, photographer, license code/version/URL, original hash, modification/crop, source-check date and what species the picture actually shows. Preserve existing original credits; CC0 attribution is encouraged.
- Use the best available taxon identification and image evidence. Hold mixed-species/off-target photographs, taxon-concept disputes, and genuinely ambiguous identifications. Do not turn recognizable but non-diagnostic recognition photos into asserted anatomy proof; no new BONAP/Hays-county native designation merely because a photo is from Texas.
- A public repository has publicly accessible branches and history. **Never upload restricted, unverified, or private-review-only image bytes into any public branch, even staging.** Preserve restricted originals in a separate private/off-GitHub store if required; keep a reference and missing/hold status on GitHub without exposing those bytes.

## Fast family-batch workflow
**1. Reconcile:** route by current family registry; index ZIP/individual photo IDs, author/license, original SHA-256, physical bytes and already-published image hashes, avoiding same-image duplicates and repetitive near-identical views. Use existing archives before new downloading.
**2. Screen in bulk:** quick contact sheets for plant identity and visual utility. Classify photo into `READY_FOR_RIGHTS_ID_QA`, `HOLD_SOURCE_OR_TAXON`, `ALREADY_PUBLISHED`, `NOT_USEFUL_FOR_THIS_ROLE`. Never count candidate photos as installed.
**3. Verify & release:** check exact source/rights and ID for each selected item; put eligible photo bytes and credits into the assigned family publisher, following existing approval fields honestly; publish general view immediately without arrow/lesson review. Preserve the user's original files; keep practical batches at <=100 files and each photo <=25 MB.
**4. Confirm visibility:** verify media exists in repository, species card references it, captions/source/license links render, gallery/index totals match, automated site tests pass and GitHub Pages serves it. Distinguish `staged`, `GitHub hosted`, `site indexed`, `Pages verified`. Fix failing outdated fixed-count tests rather than freezing a growing gallery.
**5. Deferred enrichment:** log true remaining anatomical targets (ligule, glume, node, tendril, flowers, etc.) once; add arrows only after image/label placements are visually checked. A user-reported wrong photo, ID, orientation, annotation or caption receives immediate correction priority.

## Boundaries / consistency
- New botanical work goes to **the family-owned repository and branch from the active routing registry**. Do not send new photo content to the original `Crking92/Hays-County-Botany` read-only fallback.
- Do not change repository visibility, rewrite history, auto-restart dormant background jobs, or bypass taxonomic/range holds as a shortcut.
- Site-specific publisher code can be stricter than this policy. In that case, record the integration gap explicitly and update/test the publisher separately instead of misrepresenting installation.
- Report each pass compactly: processed, duplicate, eligible, source/ID held, GitHub hosted, live verified, species with photos, next photo gaps. **Published photos are the progress metric**; review packets are supporting records, not substitutes.
